# gumgumi-cinematic

기준 샘플(`/home/lee/project/claude-animation/gumgumi-intro/`, 수정 금지)의 그림 품질을 **Sonnet 에이전트로** 재현하는 것이 목표다. 운영 현황(예약 큐·제작 방식 변경)은 `/home/lee/project/.claude/shortform/cinematic/STATUS.md`가 SSOT이고, 배치가 끝날 때마다 메인이 갱신한다.

## 과학 설명 설계 원칙

- **설명 사슬이 먼저, 그림은 그 다음**: 질문 -> 의외성 -> 인과 고리 3~5개 -> 답. 고리마다 설명 자막 1개와 그 고리를 이해시키는 그림을 붙인다.
- **두 템포**: 액션(A)은 빠르게, 설명(E)은 2~4초에 hold. E가 55% 이상. 권장 25~45초.
- **굼구미는 실험자·안내자**: 실제 원인(온도, 빛 등)을 조작하고 가리킨다. 물리적 원인을 대신하지 않는다.
- **내레이션이 설명을 이끈다**: 채널 목소리 TTS, 자막은 내레이션 문장 그대로, 굼구미 입이 맞춰 움직인다. 스토리보드 타이밍은 내레이션 구간 앵커로 적는다.
- **채널 인트로·제목카드·아웃트로를 그대로 붙인다**: Remotion 브랜드 자산을 렌더해 앞뒤에 붙인다. 제목카드가 주제를 먼저 알려준다.
- **훅은 설명 없는 일상 장면부터**.
- **작성자와 검토자 분리**: 쓴 에이전트가 아닌 리뷰어가 시청자 시점으로 이해 가능 여부를 판정한다.

## 절차

### 1. 기획

`gumgumi-cinematic-planner`를 스폰한다(model: sonnet). 프롬프트에 다음을 적는다.
- 에피소드 번호 `c<NN>`(메인이 `ls shortform/cinematic/`로 정해 준다. 병렬 기획 때 에이전트가 각자 세면 번호가 겹친다)
- 주제(있으면). 없으면 분야(몸·동물·빛·소리·우주·날씨·음식 등)를 지정해 직전 편들과 겹치지 않게 한다
- 비율(기본 9:16)
- "보고 15줄 이내"

정의파일에 이미 있는 규칙(ko만, 30자 이내, 훅은 일상 장면, Sound 칸, hold 1초)은 프롬프트에 다시 적지 않는다.
돌아오면 `ls`로 파일 6개(01-fact, 02-explain, narration-ko.json, 03-text, 04-storyboard, 05-meta)가 실제로 있는지만 확인한다.

### 2. 설명 검토 (최대 2라운드)

`gumgumi-explain-reviewer`를 스폰한다(model: sonnet, 기획 폴더 경로 전달).
- `PASS`면 3단계로 간다.
- `FIX`면 같은 planner에 SendMessage로 "수정 모드, 06-review.md 지적만 고쳐라"를 보내고, 리뷰어를 새로 스폰해 "2라운드, 06-review.md에 덧붙여라"로 다시 판정한다(리뷰어는 같은 파일에 라운드 절을 추가한다).
- 2라운드 뒤에도 `FIX`면 남은 지적을 사용자 승인 단계에 함께 보여준다. 3라운드 이상 돌리지 않는다.
- 리뷰어가 `PASS`를 줘도 경미한 지적(hold 0.1초 부족 등)이 남아 있으면 그 지적을 애니메이터 스폰 프롬프트에 한 줄로 넘긴다(planner를 다시 돌리지 않는다).

### 3. 정지점: 스토리보드 승인

사용자에게 다음을 보여주고 승인을 받는다.
- `05-meta.md` 제목
- `02-explain.md` 설명 사슬(질문, 고리, 답)과 한국어 내레이션 전문
- `04-storyboard.md` 표 전체
- 리뷰 판정과 남은 지적

수정 요청은 같은 planner에 SendMessage로 되돌린다. 승인 전에 애니메이터를 돌리지 않는다.

### 4. 애니메이션

`gumgumi-animator`를 스폰한다. 프롬프트에 다음을 모두 적는다(서브에이전트는 대화 이력을 모른다).
- 기획 폴더 절대경로
- 비율
- 작업 폴더(아직 없어야 한다)
- 출력 경로(위 경로 규칙의 `shorts/ko/[C<N>] <한국어 제목>.mp4` 실제 파일명)
- 참고 구현: 직전 편 작업 폴더 1개(가장 비슷한 기법을 쓴 편)
- 리뷰에서 남은 경미한 지적(있을 때만)
- "보고 15줄 이내"

**애니메이터는 한 번에 1편만 스폰한다.** 끝나면 `ls`로 `shorts/ko/`에 출력 파일이 실제로 생겼는지 확인한 뒤 다음 편을 스폰한다. 여러 편을 병렬로 돌리지 않는다(2026-09-28 사용자 중단 사례, 메모리 `feedback_gumgumi_ko_only_sequential`).

**모델**: 기본 `sonnet`이다. 사용자가 결과를 보고 퀄리티가 부족하다고 하면, 그 에피소드에 한해 다시 돌리되 메인 세션이 Fable인 동안은 `model: opus` 서브에이전트 대신 `fork`(메인 모델·전체 맥락)로 가져온다(2026-09-26 사용자가 상향을 미리 승인했으므로 다시 묻지 않는다, `rules/performance.md` 10-08 개정). 다시 돌릴 때는 기존 작업 폴더를 덮어쓰지 않도록 `c<NN>-<slug>-r2`처럼 새 작업 폴더를 준다.

### 5. 보고

사용자에게 다음을 알린다.
- 최종 파일 절대경로
- ffprobe 수치
- 애니메이터가 단순화하거나 못 한 비트

스크린샷이나 영상 캡처로 품질을 자체 판정하지 않는다(메모리 `feedback_no_visual_verification`). 애니메이터의 정지컷 점검은 제작 과정의 일부라 예외다. 영상은 사용자가 본다.

## 여러 편을 묶어 만들 때 (2026-10-05 확정 운영 방식)

- **기획은 5편씩 병렬**: planner 5개를 한 메시지에 스폰하되 번호(`c<NN>`)와 분야를 메인이 미리 나눠 준다. 리뷰도 편별로 병렬이다. 승인(3단계)은 5편을 한 번에 보여주고 받는다.
- **제작은 1편씩 순차**: 4단계 규칙 그대로. 렌더는 CPU 작업이라 병렬로 돌려도 빨라지지 않고, 진행 상황을 편별로 확인할 수 없게 된다.
- 배치가 끝나면 `STATUS.md`의 제작·예약 현황과 "제작 방식" 절을 갱신한다. 유튜브 예약 업로드는 별도 작업이며 방법·형식은 `STATUS.md` "업로드 형식" 절(메모리 `reference_gumgumi_youtube_scheduled_upload`)을 따른다.
- 애니메이터가 반복해서 같은 결함을 내면(예: 라벨 지시선 축소, 오디오 클리핑) 그 규칙을 `gumgumi-animator.md`에 한 줄로 추가하고 스폰 프롬프트에서는 뺀다.
