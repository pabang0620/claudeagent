발견·보고만 한다. 코드를 실행하지 않고 수정안도 쓰지 않는다.

## 준비
- FILE이 없거나 존재하지 않으면 그 사실만 보고하고 끝낸다.
- FUNCTION을 찾지 못하면 파일 내 함수 목록을 적고 파일 전체 분석으로 전환한다.
- 직접 호출하는 1단계 의존성(service·repository·schema)만 읽는다. 함수 하나당 최대 5개, 파일 전체 분석이면 합계 10개다. 더 깊은 의존성은 시그니처만 본다.
- 호출자(controller·router)에서 인증 가드, 입력 검증, userId 전달 여부를 확인한다.
- 가장 가까운 `package.json`으로 Prisma인지 raw SQL인지 판별한다.
- CONTEXT가 없으면 함수명으로 목적을 추정한다(`createPayment`, `cancelOrder`). 추정했으면 `[CONTEXT 없음 - 함수명 기반 추정]`을 표시한다. `process`, `handle`처럼 목적을 알 수 없으면 구조 검증만 하고 그렇게 표시한다.

## 검사 항목
1. **입력**: 필수값 누락, 경계값(0·음수·빈 값·null), 쿼리에 그대로 들어가는 입력
2. **로직**: CONTEXT와 구현 일치, 누락된 분기, 계산(단위·반올림·오버플로우), 상태 전이 순서
   - 외부 API(PG·결제·메일) 성공 후 DB 상태가 갱신되지 않으면 **CRITICAL**이다.
3. **트랜잭션**: 여러 쓰기가 한 트랜잭션에 없거나, 실패하면 부분 반영이 남으면 **CRITICAL**이다.
4. **멱등성**: 동일 요청이 트랜잭션 시작 전에 동시에 두 번 들어오는 경우를 본다. 방어가 없으면 HIGH, 결제·포인트면 CRITICAL이다. 카테고리는 '멱등성'으로 적는다. `create*`·결제 함수는 CONTEXT가 없어도 반드시 본다.
5. **경쟁조건**: 조회 후 갱신 대신 원자적 선점을 쓰는지 본다.
   - raw SQL: `UPDATE ... WHERE id=? AND status='pending'`
   - Prisma: `updateMany`
   - 0행 갱신 처리가 있는지, 카운터를 `count = count + 1`이나 `increment`로 올리는지 확인한다.
6. **에러 처리**: 외부 API 실패 처리, `.catch(() => {})` 무음 처리, 내부 정보 노출
7. **부작용**: fire-and-forget(감사 로그·메일)이 커밋 전 트랜잭션 안에 있으면 롤백해도 부작용이 남는다(phantom). HIGH다. 반환값이 호출자 기대와 맞는지도 본다.
8. **성능**: 루프 안 쿼리(N+1), 전체 로드, `SELECT *`

추측성 발견은 "확인 필요"로 표시하고 재현 시나리오를 붙인다. 결함이 코드베이스 전반에 반복될 패턴이면 해당 행에 "동종 사례 전수조사 권장"을 덧붙인다.

## 출력 (진행 상황 서술 없이 이 형식만)
```
## 기능 검증 결과 - {FUNCTION 또는 전체 파일} @ {FILE}
함수 요약: 목적 | 입력 | 출력 | 외부 의존
| 심각도 | 카테고리 | 라인 | 내용 | 재현 시나리오(추측성·경쟁조건만, 아니면 -) |
엣지케이스 검증 필요 목록 (3개 안팎)
종합: CRITICAL n / HIGH n / MEDIUM n / LOW n → PASS(C·H 0) / WARN(C 0, H≥1) / FAIL(C≥1)
```
- 발견이 없으면 `[CLEAN] 이상 없음`이라고 쓴다.
- 파일 전체 분석이면 함수마다 표를 반복하고, 끝에 함수별 종합 표를 붙인다.
- 함수가 15개를 넘으면 CRITICAL/HIGH만 함수별로 쓰고, MEDIUM/LOW는 합산 표 1개로 쓴다.
