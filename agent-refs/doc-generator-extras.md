# doc-generator 참조 - 데이터 예시·커버리지 매트릭스·레드팀·근거자료

doc-generator 정의파일에서 옮긴 내용이다(2026-10-01 prompt-audit). 정의파일이 가리킬 때만 읽는다.

## 1. docxtpl 데이터 예시

**계약서 데이터 예시:**
```json
{
  "title": "프리랜서 업무 계약서", "contract_number": "2026-001", "contract_date": "2026년 6월 25일",
  "party_a_name": "주식회사 OOO", "party_a_rep": "홍길동",
  "party_b_name": "이원호", "party_b_birth": "1990년 1월 1일",
  "article_1": "본 계약은 ...", "start_date": "2026년 7월 1일", "end_date": "2026년 12월 31일",
  "article_3": "보수는 월 OOO만원으로 한다.", "article_4": "기타 사항은 협의하여 결정한다."
}
```
**제안서 데이터 예시:**
```json
{
  "title": "웹사이트 구축 제안서", "date": "2026년 6월 25일", "recipient": "주식회사 OOO", "author": "이원호",
  "background": "현재 홈페이지가 노후화되어 ...", "content": "반응형 웹사이트 구축을 제안드립니다.",
  "expected_effect": "방문자 전환율 30% 향상 예상", "budget": "총 1,500만원", "schedule": "2026년 8월 ~ 10월"
}
```
**보고서 데이터 예시:**
```json
{
  "title": "2026년 상반기 성과 보고서", "date": "2026년 6월 25일", "author": "이원호", "department": "개발팀",
  "summary": "상반기 주요 성과 요약 ...", "body": "세부 내용 ...", "conclusion": "하반기 개선 방향 ..."
}
```

## 2. STEP 1-A 커버리지 매트릭스

## STEP 1-A: 제안서 전용 - RFP 요구항목 커버리지 매트릭스 (조건부)

**적용 조건**: 문서 종류가 **제안서**이고 요청에 RFP(제안요청서) 핵심 요구사항이 포함되어 있을 때만 실행한다. 계약서·보고서 등 다른 문서 종류이거나, 제안서라도 RFP 정보가 없으면 이 STEP을 건너뛴다(STEP 0 게이트 항목을 추가하지 않는다 - RFP 미제공 시 질문하지 않고 생략).

RFP 내용에서 핵심 요구사항을 추출해 **커버리지 매트릭스**를 만든다:

| 요구항목ID | 요구내용 | 배점(있으면) | 대응 섹션 |
|-----------|---------|-------------|-----------|
| R1 | (RFP에서 추출한 요구사항) | (배점 또는 "-") | (문서 내 대응 섹션명) |

- 요구항목ID는 `R1, R2, ...` 순번으로 부여한다.
- "대응 섹션"은 해당 요구사항을 다루는 문서 내 섹션(필드명 또는 소제목)으로 채운다.
- **Pandoc 방식(STEP 2-B)**: 이 표를 마크다운 본문에 별도 섹션(`## RFP 요구사항 커버리지`)으로 그대로 포함한다.
- **docxtpl 방식(STEP 2-A)**: STEP 2-A에서 `list_vars.py`로 확인한 변수 목록에 `content` 등 자유서술 텍스트 필드가 있으면 그 안에 "[RFP 요구사항 커버리지]" 소제목과 텍스트 목록 형태로 포함한다(표 대신 나열, 목록에 없는 키는 넣지 않는 원칙 유지). 적합한 필드가 없으면 문서 본문에는 넣지 않고 STEP 3 보고 첨부로만 제공한다.
- "대응 섹션"이 비어있는 요구항목은 STEP 3 보고에서 **미대응 요구항목**으로 표시한다.

## 3. STEP 2.5 레드팀 자체검토

## STEP 2.5: 레드팀 자체검토 (조건부 - 산출물 완성 직후, STEP 3 보고 전. 문서를 수정하지 않는다)

**적용 대상**: STEP 0에서 확인한 문서 종류가 제안서·보고서·기획안 등 **경쟁/심사 맥락 문서**일 때만 수행한다. **계약서·공문서 등 법적 효력 문서는 이 단계를 생략한다** (당사자 간 합의문서에 "공격 포인트" 프레임이 부적합하다).

산출물(.docx)이 정상 생성된 뒤, STEP 3 보고 전에 두 관점으로 자체 검토한다. **이 단계는 발견사항을 목록으로 정리해 STEP 3 보고에 첨부하기만 한다. 문서(.docx)를 이 단계에서 자동으로 고치지 않는다 - 사용자가 검토·승인한 뒤에만 반영한다.** 근거는 방금 구성한 JSON 데이터(STEP 2-A) 또는 마크다운 초안(STEP 2-B) 내용으로 삼는다 (.docx를 다시 열어 읽지 않는다).

- **심사위원 시각**: 요청에 포함된 RFP·심사기준·배점 정보가 있으면 그 기준 대비 약한 부분을, 없으면 일반적 설득력 관점에서 정량 근거(수치·데이터)가 빈약한 주장, 차별성이 불명확한 항목을 짚는다. STEP 1-A **커버리지 매트릭스**가 존재하면 미대응·약한 대응 항목을 우선 지적 대상으로 삼는다. 없어도 이 검토는 독립적으로 수행한다.
- **경쟁사 시각**: 경쟁 제안사·평가자가 이 문서의 허점으로 지목할 만한 방어 취약점(모호한 근거, 검증되지 않은 실적, 리스크 대응 부재 등)을 짚는다.

**출력 형식**:
| 위치(항목/섹션) | 지적 내용 | 권고 보완방향 |
|---|---|---|
| 예: expected_effect | 정성적 서술만 있고 수치 목표 없음 | 전환율·매출 등 정량 목표치 추가 권고 |

발견사항이 없으면 "레드팀 검토 결과 특이 지적사항 없음"으로 짧게 기록한다.

## 4. 근거자료(evidence) 활용

### 근거자료(evidence 파일) - 선택 입력 (STEP 0 게이트와 무관)

web-crawler·deep-research가 생성한 `evidence_*.md` 경로가 요청에 포함되어 있으면 **Read 도구**로 읽어 본문 작성에 활용한다. **경로가 없어도 STEP 0 게이트·이후 단계는 기존과 동일하게 진행한다** (필수 항목 아님, 재질문하지 않음).
- 표의 근거ID·핵심 내용/수치·출처·발행일을 인용해 보고서·제안서 본문 근거 문장을 구성한다.
- 활용한 수치·주장에는 evidence 파일에 부여된 근거ID(형식 `E-[슬러그]-[2자리]`)를 문장 끝에 대괄호 각주로 표기한다 (예: "콘텐츠 시장 규모는 150조원이다[E-contents2026-01]."). evidence 파일이 없으면 이 표기는 생략한다.

## 5. 환경 준비 블록 (첫 Bash 호출)

```bash
BASE=$(find "$HOME" -maxdepth 4 -type d -name "doc-generator" 2>/dev/null | head -1)
if [ -z "$BASE" ]; then
  echo "NOT_FOUND"
elif [ ! -f "$BASE/scripts/gen_docxtpl.py" ] || [ ! -f "$BASE/scripts/gen_pandoc.py" ]; then
  echo "SCRIPTS_MISSING: $BASE"
else
  echo "OK: $BASE"
  mkdir -p "$BASE/output"
  ls "$BASE/templates/"
fi
```

## 6. STEP 0 묶음 질문 예시

여러 항목이 비면 한 번에 묶어 반환한다. 예:
> "문서 생성을 위해 몇 가지 정보가 필요합니다.
> 1) 어떤 종류의 문서인가요? (계약서·제안서·보고서 등)
> 2) 문서 제목이나 주제를 알려주세요.
> 3) 들어갈 핵심 내용을 알려주세요. (당사자·기간·주요 항목 등)"
