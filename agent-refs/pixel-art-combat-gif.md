# 픽셀아트 전투 애니메이션 GIF 표준 (참조 파일)

> `agents/game-asset-artist.md`에서 "전투 애니메이션 GIF" 요청일 때만 읽는다. 사용자가
> 2026-09-10 확정한 템플릿을 이 에이전트의 기존 절대 규칙(0~5)과 결합해 재구성한 것 -
> 프롬프트 원문을 그대로 복붙하지 않고 매번 대상 캐릭터·프로젝트 스타일에 맞게 설계한다
> ("잘 녹여서 원하는대로 설계" - 사용자 확정).

## 작업 순서 원칙 (2026-09-10 확정 - 후처리를 먼저 얹지 않는다)

**시트 생성 → 후처리(프레임분리+GIF조립+알파변환) 전부를 한 번에 하지 않는다.** 먼저
시트 이미지 1장만 생성해서 그대로(후처리 없이) 사용자에게 전달하고, **사용자가 시트
자체를 보고 괜찮다고 확인한 뒤에만** 프레임 분리·GIF 조립·알파 변환 등 후처리로 넘어간다.

이유(2026-09-10 실측): 매 라운드 즉석으로 새로 짜는 후처리 스크립트(알파 변환, geodesic
팽창, 크롭 재계산 등)가 그 자체로 반복 버그를 유입시켜 원래 괜찮았을 생성 결과를 오히려
망가뜨렸다(캐릭터 본체가 투명해지는 등 후처리 전에는 없던 결함 발생). 사용자 원문: "그럴
필요 없이 넌 그냥 16시트 이미지만 생성해서 나한테 전달해주면 내가 보면 되는거야." 생성
자체의 품질(포즈·구도·캐릭터 유사도)과 후처리 파이프라인의 정확성은 별개 문제이므로 섞어서
반복하지 않는다 - 생성 결과가 확정된 뒤에만 후처리 파이프라인을 1회 적용한다.

## 요청 판별

캐릭터 레퍼런스 이미지 + "전투 애니메이션", "픽셀아트 GIF", "16프레임 스프라이트" 등의
요청이 오면 이 문서를 적용한다. 일반 아이콘·타일·정적 포즈 시트는 해당 없음(기존 절대
규칙만 적용).

## 캐릭터 원형 유지

- 레퍼런스 이미지의 헤어스타일·의상·색상·무기·비율·고유 특징을 프롬프트에 구체적으로
  서술해 고정한다(절대 규칙 2와 동일 원칙 - "대략 비슷하게" 금지).
- 캐릭터에 이름이 있으면 프롬프트에 이름을 명시해도 된다.
- 16프레임 전체에서 캐릭터 정체성·머리/몸 비율·의상 구조·무기 형태·배색 관계가 흔들리지
  않게 프롬프트에 반복해서 못박는다.

## 공격 동작 설계 우선순위

1. 캐릭터에 기존 설정(무기·능력)이 있으면 그것을 따른다.
2. 없으면 외형에서 합리적인 공격을 자동 유추한다 - 무기가 있으면 무기 중심, 능력이
   불명확하면 어울리는 원소/에너지 효과 또는 자연스러운 근접 물리 공격.
3. 6단계를 반드시 순서대로 포함: **준비 자세 → 예비 동작 → 공격 → 타격의 정점 → 효과
   소멸 → 원래 자세 복귀**. 16프레임에 이 6단계를 분배하고, 16번째 프레임이 1번째로
   자연스럽게 이어지게 한다(루프 연속성 - gutter/포즈 모두).
4. 정지 이미지를 이동·회전·확대축소로 대체 금지 - 프레임마다 실제 자세·무게중심 이동·
   팔다리 힘 전달·무기 궤적이 달라져야 한다(절대 규칙 2의 연장).

## 프롬프트 구성 (1회 생성 - 절대 규칙 0의 "시트 1장 원칙" 그대로 적용)

- 스타일: 16비트 게임풍 픽셀아트, 명확한 윤곽선, 선명한 픽셀 가장자리, 절제되고 통일된
  팔레트. 채색·무기·특수효과 표현 방식이 전 프레임에서 일관되어야 함을 명시.
- 레이아웃: 정확히 4열×4행 16프레임, 좌→우 위→아래 순서, 카메라 고정, 캐릭터 크기·지면
  기준선·정렬 기준점 고정, 셀마다 캐릭터 전신이 잘리지 않고 온전히 포함.
- **행/열 크기를 "동일하게"라고 뭉뚱그리지 말고 실제 숫자로 못박는다(2026-09-10 확정 -
  뭉뚱그린 지시는 지켜지지 않는 게 반복 재현됨)**: 목표 캔버스 전체 크기와 셀 1개 크기를
  구체적 숫자로 프롬프트에 명시한다(예: "the entire sheet is exactly 1312×1200 pixels,
  divided into a strict 4×4 grid where every single cell is exactly 328×300 pixels - all 4
  rows must have exactly the same height, all 4 columns must have exactly the same width,
  with zero variation"). CHARACTERS.md/WORLD_AND_FX.md에 셀 크기 스펙이 있으면 그 숫자를
  그대로 가져다 쓴다. "모든 셀 동일 크기"라고만 쓰면 실제로는 행마다 22~40px씩 다르게
  나오는 현상이 반복 확인됐다 - 숫자를 박아야 모델이 그리드를 실제로 지킨다.
- 그럼에도 모델이 정확한 그리드를 안 지킬 가능성은 남아있으므로, 후처리 단계에서 등분할
  좌표를 맹신하지 않고 **실제 알파 콘텐츠 경계를 실측해서 행/열 경계를 다시 계산**하는
  안전장치(아래 "생성 후 처리" 절)는 계속 유지한다 - 프롬프트 강화는 예방이지 보장이 아니다.
- 금지 문구를 명시적으로 못박는다: 텍스트, 프레임 번호, 격자선, 워터마크, 배경 장면
  (절대 규칙 0의 "한 장으로" 문구와 함께 넣는다).
- 배경: 투명 배경을 요청하지 않는다(모델이 진짜 알파 대신 체커보드 무늬를 픽셀로 그려 넣는
  경우가 반복 확인됨 - 2026-09-10 법사 캐릭터 3회 전부). 절대 규칙 3대로 순수 마젠타(#FF00FF)
  단색 배경을 요청하고 후처리로 알파를 만든다. 거터도 같은 마젠타 단색으로 요구. 흰 배경
  소스를 받은 경우에만 아래 "흰 배경 → 알파 변환" 절차를 쓴다.
- 발광 효과는 과하지 않게 범위를 한정해서 요구(전체가 번쩍이는 결과 방지).
- **셀 경계 절대 준수(모델이 자주 어기는 지점 - 실측 재현됨)**: "each of the 16 cells is a
  hard, non-negotiable boundary - no character part, weapon, magic beam, spark, or glow
  effect may extend past its own cell into a neighboring cell, even partially. If an effect
  would naturally overflow the cell (e.g. a long-range beam), scale it down or reframe it so
  it fits entirely within the cell." 이걸 빠뜨리면 이펙트가 인접 셀로 삐져나와 그려지고,
  이후 등분할 크롭 시 "오른쪽이 잘려서 왼쪽에 다시 나타나는 것처럼 보이는" wrap-around
  결함으로 나타난다(2026-09-10 실측 - row2 원거리 캐스팅 구간에서 재현, 프롬프트 강화로
  해결됨). 후처리로 고칠 수 없는 원본 생성 단계의 문제이므로 반드시 사전에 못박는다.
- **캐릭터 전신 스케일 고정(포즈에 따른 자연스러운 신장 변화와 구분)**: "the character's
  overall body scale (crown of head to sole of feet) must remain visually consistent across
  all 16 cells. If a pose involves crouching, a wide stance, or leaning, represent it through
  actual joint/limb bending - do NOT shrink or enlarge the whole character sprite to imply a
  different pose." 크라우치·와이드 스탠스 자체는 정당한 신장 감소를 동반하므로 완전히
  0%로 맞출 수는 없다 - QA에서 "서 있는 프레임끼리만" 비교하는 이유가 여기 있다(아래 QA
  표 5-1 참고).
- **의도하지 않은 부속물은 "금지"가 아니라 "긍정 서술"로 막는다 (중요 - 부정 프롬프트 역효과
  주의, 2026-09-10 확정)**: "뿔 넣지 마", "이상한 돌출부 없이" 처럼 **없어야 할 대상을
  이름으로 콕 집어 부정문으로 쓰지 않는다** - 이미지 생성 모델은 부정을 잘 처리하지 못해서
  오히려 그 단어가 언급됐다는 이유로 해당 형체를 그려 넣는 역효과가 실제로 재현됐다(뿔이
  전혀 문제였는지 재현 확인도 안 됐는데 "뿔 없이"라는 프롬프트 자체가 원인일 가능성).
  대신 **머리에 있어야 할 것만 긍정문으로 정확히 서술**한다: "the head shows only
  [레퍼런스의 실제 요소, 예: a dark hood with the exact silhouette shown in the reference
  image] - nothing else." 특정 오브젝트명(뿔·뿔모양 등)을 프롬프트에 아예 등장시키지 않는
  것이 원칙이다. 여러 번 생성해도 같은 특정 결함이 반복 재현될 때만, 그 결함을 부정문이
  아니라 "정확한 형태를 다시 서술"하는 방식으로 좁혀서 대응한다.

## 생성 후 처리 - 프레임 분리 + GIF 조립 (이 카테고리 전용 후처리)

생성 모델(flow-nanobanana)이 만드는 건 4×4 스프라이트 시트 1장(JPEG)뿐이다. 16개 개별 PNG와 무한반복 GIF는
이 에이전트가 Bash(Python PIL)로 직접 후처리한다. 매 요청마다 인라인 스크립트로 처리하고,
반복 사용 빈도가 높아지면 그때 `.claude/agent-refs/scripts/`에 재사용 스크립트로 승격한다
(지금 미리 만들어두지 않는다 - 실제 출력을 보기 전에 만든 변환 스크립트는 검증 안 된 채로
남는다).

핵심 요구사항:
- **행/열 경계는 등분할 좌표를 그대로 쓰지 않고, 먼저 실제 투명 갭(행 사이·열 사이의
  거의 완전 투명한 구간)을 실측해서 그 중간점을 경계로 삼는다.** 프롬프트를 아무리
  강화해도 모델이 요청한 정확한 그리드 치수를 안 지키는 경우가 실제로 반복됐다(행 높이가
  등분할값보다 6~40px씩 큰 채로 나온 사례). 등분할 좌표를 맹신하고 자르면 캐릭터 하반신·
  이펙트가 잘리므로, 4행/4열 각각에 대해 alpha가 거의 0에 가까운 구간(행 사이·열 사이)을
  스캔해서 실제 경계를 찾은 뒤 그 경계로 크롭한다. 그 다음 각 셀 내부 캐릭터의 실제
  바운딩은 알파 연결요소로 확인한다(절대 규칙 3과 동일 사고방식 - 단순 좌표 등분할만으로
  "잘리지 않았는지"를 판정하지 않는다).
- GIF는 프레임별 `duration` 배열로 타이밍을 차등 준다 - 준비 자세·예비 동작은 보통 속도
  (약 90~110ms), 공격 구간은 짧게(약 60~80ms), 타격의 정점은 살짝 길게(약 120~150ms),
  효과 소멸은 보통 속도(약 90~110ms), 복귀 구간은 길게(약 100~130ms). 16개 duration의
  합이 1.5~2초 범위에 들어오는지 실제로 더해서 확인하고, 벗어나면 프레임별 값을 조정한다
  (자동 검증 대상 - 아래 QA 표 참고).
- 16프레임 전체를 **동일한 팔레트, 동일한 투명 인덱스**로 저장한다. 프레임마다 독립적으로
  quantize(RGBA→P 변환)하면 같은 인덱스 번호가 프레임마다 다른 색을 가리켜 재생 중 특정
  프레임만 색이 튀거나 엉뚱한 영역이 투명 처리되는 결함이 생긴다. PIL이면 16프레임을 합쳐
  하나의 공용 팔레트를 먼저 만들고(`Image.quantize`를 한 번에 적용하거나 첫 프레임 팔레트를
  나머지에 강제 적용) 그 팔레트로 전 프레임을 저장한 뒤, 동일한 투명 인덱스 번호를
  `transparency=`에 지정한다.
- 투명 GIF 저장 시 `save_all=True, loop=0, transparency=<공용 투명 인덱스>, disposal=2`로
  이전 프레임 잔상을 방지한다(disposal=2 = 배경으로 복원 후 다음 프레임 그리기).
- 저장 후 프레임별 가장자리 alpha를 실측(절대 규칙 3의 스크립트 재사용)해 잔여 반투명
  근백색 픽셀이 없는지 확인한다 - "재생해보니 깨끗해 보인다"는 판정 근거가 아니다.
- **흰 배경 → 알파 변환은 단순 임계값 하나로 끝나지 않는다(2026-09-10 3회 반복 실패 후
  확정된 방법)**: 테두리에 연결된 저채도 영역(chroma 낮음)을 먼저 투명 처리한 뒤,
  거기서 **연결성 기반으로(geodesic 팽창 - 이미 투명 처리된 영역에 인접한 픽셀만 조건부로
  추가 흡수, 전역 좌표 임계값 아님)** 안티에일리어싱 헤일로나 체커보드 잔여를 마저 제거한다.
  단순 "RGB≥240 전역 스캔" 하나만 쓰면 (a) 캐릭터 실루엣 안에 완전히 갇힌 배경 잔여
  구멍(팔-몸통 사이, 다리 사이, 머리카락 컬 사이)을 놓치거나, (b) 머리카락 하이라이트·
  무기 크리스탈/오브의 흰색 스파클처럼 의도된 디자인 요소까지 함께 지워버린다. 처리 후
  반드시 확대 크롭으로 "지워진 게 진짜 배경 잔여물이었는지, 의도된 아트 요소는 아니었는지"
  육안 대조한다.
