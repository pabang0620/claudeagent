# game-asset-artist 참조 - 흰 배경 키잉·자주 틀린 것

game-asset-artist 정의파일에서 옮긴 내용이다(2026-10-01 prompt-audit). 정의파일이 가리킬 때만 읽는다.

## 1. 흰 배경에서 알파를 뽑는 경우

**흰 배경에서 후처리로 알파를 뽑아야 하는 경우** (예: 참고용 없이 순수 채색 아이콘이라
흰 배경 크롭이 더 간단할 때):
전역 색상 임계값 크롭이 아니라 **테두리에서 연결된 흰색 영역만** 배경으로 간주해
투명 처리한다(`scipy.ndimage.label`로 이미지 가장자리에 닿은 흰색 연결요소만 alpha=0,
내부가 흰색이어도 테두리와 안 닿아 있으면 보존). 순수 임계값(rgb_sum 기준 단순 크롭)만
쓰면 흰색/크림색 내용물까지 함께 지워지거나, 반대로 가장자리에 반투명 근백색 픽셀이
남아 "흰 테두리/회색 얼룩" 결함이 생긴다(이 프로젝트에서 실제로 3회 반복된 사고) - 크롭
후 반드시 아래처럼 가장자리 픽셀을 Bash(PIL/numpy)로 실측해 잔여 0을 확인한다:

```python
# 가장자리 opaque 근백색 픽셀 잔존 여부 확인 (0이어야 함)
for row in [0, h-1]:
    for col in range(w):
        r,g,b,a = arr[row,col]
        assert not (a > 200 and int(r)+int(g)+int(b) > 650)
```

## 2. 자주 틀린 것 (다른 게임 프로젝트 실측 이력 - 반복 금지)

0. **변형을 낱개로 쪼개 생성** → 생성 한도를 소진해 정작 필요한 걸 못 만든다. 가장
   자주·가장 비싸게 실패한 지점이다.
1. **캔버스 크기를 임의로 512로 퉁기기** → 실제 표시 크기와 어긋나 왜곡·여백 사고.
2. **컨셉 승인 없이 바로 액션 포즈 시트로 감** → 사용자가 원치 않는 디자인으로 여러
   포즈를 낭비 생성하게 된다. 규칙 1의 승인 게이트를 건너뛰지 않는다.
3. **포즈를 "walking pose"/"attack pose"로 뭉뚱그림** → 다리 위치·무기 그립·목 정렬이
   이상해지는 실제 원인.
4. **Read 도구로 투명 여부를 판정** → 뷰어가 alpha를 무시하고 RGB를 그대로 보여준다.
   투명·가장자리 판정은 반드시 Bash(PIL/numpy) 실측.
5. **결함 발견 후 무한 재생성** → 생성 한도만 소진한다. 재시도는 최대 1회.
6. **전역 색상 임계값만으로 흰 배경 크롭** → 가장자리에 반투명 근백색 픽셀이 남아
   "흰 테두리" 결함이 생기거나, 흰색 내용물(예: 흰 갑옷)까지 지워진다. 규칙 3의
   가장자리-연결 흰색만 배경으로 간주하는 방식을 쓴다.
7. **알파가 필요한데 마젠타 배경을 지정하지 않고 생성** → 키잉할 수 없다. 생성 전에
   알파 필요 여부를 정하고 순수 마젠타(#FF00FF) 배경을 요청한다.
8. **알파가 필요하다는 이유로 Codex/gpt-image로 넘김** → 금지. 알파 필요 여부와 무관하게
   `flow-nanobanana`로 마젠타 배경을 받아 이 프로젝트의 키잉 도구로 알파를 만든다. Codex는
   Flow가 차단됐을 때만 쓴다(flow-nanobanana 0절·7절).
9. **차단 문구가 뜬 뒤 재시도·우회** → 즉시 멈추고 보고한다. 제출 간격은 브라우저 시계로 잰다.

## 3. JPEG 소스 키잉 뒤 실측 항목

Flow 결과물은 JPEG라 마젠타 경계에 색 번짐이 남을 수 있다. 굵은 검정 외곽선 화풍은 그라데이션
경계보다 강하지만, 키잉 후 반드시 Bash(PIL/numpy)로 실측한다: 코너·경계 알파 잔여 픽셀,
연결 성분 분리 여부(요소 수가 의도한 셀 수와 같은지), 체커보드성 얼룩 유무. 번짐이 실측되면
프롬프트에 피사체와 배경 사이 여백을 더 두도록 요청해 1회만 다시 시도한다.
키 조건 기본값과 헤일로 대응은 flow-nanobanana 5절. 투명·가장자리 판정에 Read 도구를 쓰지
않는다(뷰어가 alpha를 무시한다).

## 4. 실제 렌더 크기 역산 방법

- Unity: 관련 `RectTransform`/`sizeDelta`/`Image`를 만드는 C# 코드를 Grep으로 찾아 실제 크기(유닛)를 읽는다.
- Godot: 관련 `.tscn`의 `offset_left/top/right/bottom` 또는 `size`를 읽는다.
- 생성 후 저장된 파일의 실제 크기를 실측해 인계한다:
```bash
python3 -c "from PIL import Image; im = Image.open('<경로>'); print(im.size, im.mode)"
```

## 5. 동작·포즈 서술 세부

- 동작 프레임: 어느 쪽 다리·팔이 어떻게 움직이는지까지 쓴다.
- 무기를 쥐는 포즈: 손과 무기의 접촉을 명시한다("fingers fully wrapped around the hilt, no floating weapon").
- 머리 위치·비율: 목-척추 정렬과 전체 대비 머리 비율을 모든 프레임에서 고정.
- 셀 간 캐릭터 비율: 시트 안 여러 셀의 크기 배율이 달라지지 않게 명시.
- 팔다리 누락·여분 방지 문구("exactly two arms, exactly two legs").
- 없어야 할 것을 이름으로 부정문에 넣지 않는다(모델이 그 단어를 그려 넣는다). 있어야 할 것만 긍정문으로 서술한다.
